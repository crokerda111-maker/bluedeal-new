1차 공개의 제안 목표는 기존 가격표 유지, 대표 부품 20개 정보, 완본체 3종·반본체 3종의 검증된 비교다. 이는 현재 달성 수나 보장 일정이 아니다. 접근 가능한 근거와 모델 중복 여부를 확인해 범위를 조정한다. 계정 인증·제휴 승인·상업적 이용 범위·외부 응답에 걸린 시간은 별도 의존 조건으로 기록한다.

초기 실행 주기는 정기 수집 09·17시, 공개 경로 상태 확인 30분, 백업 하루 1회를 설계 기준으로 삼되 허용된 요청량과 측정 결과로 조정한다. 자동 수집 제한이 있는 출처에 이 주기를 강제로 적용하지 않는다. AI는 원본 변경이 있는 새로운 근거의 판단, 재현된 복잡한 장애와 기능 개발에 사용하며 정상 상태의 반복 보고는 프로그램이 작성한다. 서버/판매처 API의 요금과 요청 제한은 코덱스 한도와 별도다.

배포는 기능 하나 또는 검증 데이터 묶음마다 타입·린트·관련 테스트·빌드·모바일 확인을 마친 뒤, 기존 단계별 공개 확인 방식으로 진행한다. 원본 근거와 실제 확인 시각, 정정·복구 기록을 남긴다. 임시 공개 글·로컬 조사 자료는 대상과 보관 기준을 정한 뒤 정리하며, 기존 삭제 허용 대상을 넘어 임의로 삭제하지 않는다.

## 현재 구현

- `src/lib/valueAssessment.ts`: 근거·부품·이슈·동일 구성·가격의 타입과 평가 엔진, 수동 비용 시나리오 계산. 필수 부품·옵션·수량·재고·가격 확인 시각·주문별 배송비·명시적인 서비스 비용을 검증한다. 구성 미확인과 비교 조건 차이는 비교를 보류한다. 품질 미확인은 평균값으로 대체하지 않는다.
- `src/content/partDossiers.ts`: 공식 자료를 다시 확인한 i7-14700K 정보 1건. 실제 성능 테스트나 현재 가격·품질 점수는 등록하지 않았다. 제조사 공지가 개별 CPU 전체의 불량 또는 대응 완료를 뜻하지 않는다.
- `/evaluate`: 직접 입력한 동일 구성의 부품·배송·조건 보정 비용과 본체 결제금액 비교. 사용자 입력은 현재 판매가 검증·검증된 추천 점수로 승격되지 않는다. 시험 운영은 noindex이며 실제 상품의 종합 점수는 표시하지 않는다.
- `ops/maintenance/`: 운영 상태·오래된 가격·자료 상태 점검과 최근 핫딜 감시. 가격·점수·게시·제휴·배포를 자동으로 변경하지 않는다.

## 초안 산식의 제한

직접 구매 합계 = 동일 모델·옵션·수량의 부품 금액 + 중복을 제거한 주문별 배송비 + 명시된 조립·OS·서비스 보정 비용. 차이율 = (직접 구매 합계 − 본체 배송 포함 결제금액) / 직접 구매 합계 × 100. OS 및 보증의 차이를 확정하거나 보정할 수 없으면 동일 비교로 확정하지 않는다.

가격 45·품질 35·판매자/AS 20과 부품별 비중, 가격 차이의 점수 환산, S~D 기준은 **검토 전 초안**이다. 실사용 데이터로 검증하거나 사용자와 합의된 확정 기준이 아니다. 기본 정책은 `draft`이며 전체 데이터가 채워져도 종합 점수는 null이다. 테스트의 `reviewed`와 점수는 합성 자료만 대상으로 한다. 실제 데이터의 품질 점수와 `reviewed` 정책을 임의로 생성하지 않는다.

가격 근거는 24시간, 조사 근거는 30일을 초안 재검토 기준으로 삼는다. 출처의 게시일과 우리가 실제 읽은 시각은 다르다. 품절·미확인·오래된 가격을 무료/최저가/현재가로 취급하지 않는다. 심각한 제조사 확인 이슈의 적용 여부가 불명확하면 추가 조사를 요구하고, 적용되는데 대응 확인이 없으면 추천을 보류한다. 영향 제외·대응 적용 주장은 별도 출처가 있어야 한다. 커뮤니티 제보는 확인 사실과 구분하며 그 자체로 자동 감점하지 않는다.

## 상품 조사·평가 구현 상세

1. 과거 조사와 최근 감시의 제목 후보를 정확한 SKU·리비전·옵션으로 대조한다. 생략 제목·복수 구성·추첨은 자동 확정하지 않는다. 출처의 상업적 재사용 조건도 별도로 확인한다.
2. 실제 판매처별 수집 어댑터 또는 허용된 공식 피드를 연결한다. 모델·옵션·판매자·쿠폰·배송·재고·확인 시각이 일치하는 원본 근거와 변경 이력을 남긴다. 다나와 가격을 대체 근거로 쓰지 않는다.
3. CPU·메인보드·RAM·PSU·GPU·저장장치·케이스·쿨러의 근거를 확장한다. 제조사 사양, 독립 측정, 반복 후기, 수정·회수·펌웨어 대응을 구분한다. 파워 효율 인증만으로 전체 품질 등급을 정하지 않는다.
4. 완본체·반본체 BOM을 대조하고 실제 동일 구성 비교 사례로 초안의 비중·등급·사용 시나리오를 검토한다. 게임·작업·저전력 등 목적에 따른 차이를 설명하고 검증된 데이터부터 공개한다.
5. 서버의 정기 수집·작업 큐·재시도·알림·관측 이력으로 이전한다. 현재 앱 정기 점검은 로컬 PC와 실행 환경이 필요하며 24시간 서버 운영과 같지 않다.
6. 계정 인증, 제보 검수, 중복/자기 추천 방지, 정정 이력, 신고·관리자 도구를 만든다. 현재 닉네임 저장만으로 보상 대상자를 확정하지 않는다. 기여 보상은 플랫폼 규정·운영 조건·예산을 확인한 뒤 별도 승인으로 시행한다.

운영 공개는 검증 가능한 구체 변경안과 테스트 결과를 준비한 뒤 기존 단계별 확인 방식으로 진행한다. 유료 인프라·새 권한·경품 지급·메일 발송은 개발 승인의 범위를 넘겨 실행하지 않는다.

## 검증

`npm run test:assessment`, `python -m unittest discover -s ops/tests -p test_maintenance.py`, 타입 검사·린트·빌드. 로컬 서버가 127.0.0.1:3000에서 실행 중이면 `node ops/tests/evaluation-readonly.mjs`로 실제 SSR 입력/계산/오류·출처 표시 흐름을 확인한다. 모든 예시 가격·점수는 테스트 전용이며 운영 카탈로그에 기록하지 않는다.
